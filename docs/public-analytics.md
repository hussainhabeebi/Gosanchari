# Public GA4 activation checklist

Measurement ID: `G-J5JVRNNVKL`. The implementation is **disabled by default**.
No deployment settings, database content or Google account settings were changed.

Before enabling:

1. Publish owner-approved privacy wording at Admin → Website Settings → Website content → About and policies → Privacy policy (`/admin/content`). The current placeholder is insufficient. The disclosure must accurately describe optional Google Analytics, its purposes/data/cookies, Google processing/transfers and retention as applicable, consent and withdrawal, and the site's actual privacy practices. Obtain appropriate legal review; this document is not replacement legal wording.
2. In the GA4 web stream, disable **all Enhanced Measurement**, including history page views, form interactions, site search, outbound clicks, downloads and video events. Remove any stream event modifications/custom definitions or connected tags that collect personal information or duplicate page views. Keep Google Signals, advertising personalisation and user-provided data collection disabled. Review retention and data-sharing settings in the Google account. These account settings cannot be verified from this repository.
3. Only after those checks, set the optional Worker variable `GA4_READINESS=privacy-approved-enhanced-measurement-off` through an approved future rollout. Do not set it merely to install the code. A policy text sanity check is additional protection, not proof of legal adequacy.
4. In a fresh production-browser session, verify no Google requests or analytics cookies before consent, or after rejection. Accept and inspect requests: one `page_view` per full public document, fixed page-category URL/title, empty referrer, no query/hash/search terms/form values. Verify withdrawal removes GA cookies and stops collection. Confirm private/authenticated/customer/preview pages never receive the controller.
5. Check GA4 Realtime/DebugView with authorised account access. Confirm no duplicate events and exercise enquiry submission without sending any enquiry data. Verify mobile consent controls manually before launch.

## Data boundary

Anonymous eligible public pages only. Property pages aggregate under `/stay/property`, search under `/search`; individual property slugs and search queries are deliberately omitted. No event listeners collect form, click, search, enquiry or customer data. The official Google library can still collect technical device/browser/network information after consent; do not describe analytics as collecting no personal data whatsoever. No Google connection occurs before opt-in (basic consent mode). Advertising consent stays denied. Consent choice is stored for 180 days in localStorage and a Secure, SameSite=Lax preference cookie. Restoring acceptance requires matching records, valid timestamps, and verified writes to both stores. Older localStorage-only acceptance requires a fresh opt-in. Rejection immediately disables collection, removes the tag and its pending commands, and clears GA cookies where possible. It never reloads the page. If either preference write fails, tracking stays off and a clear status is shown. Rejection saved in either store blocks an old acceptance on the next visit. Read-only storage cannot reactivate tracking on reload. If every browser storage mechanism refuses writes, no site can durably record a choice; the current page remains disabled and tracking cannot restart while storage remains unavailable. Acceptance also fails closed unless both preference records can be saved and read back. Analytics preferences allows withdrawal at any time. After withdrawal, a later explicit acceptance is saved for the next visit; the current document remains disabled.

Server-side launch gating excludes authenticated sessions, private areas, customer links, enquiry/help/auth pages, previews, errors and unknown routes. Frontend startup additionally requires the exact production origin. Restrictive CSP permits only the official Google tag host and GA collection hosts. No pricing, quotation, CRM, schema or database behavior is altered.

## Cross-tab withdrawal

Eligible public tabs listen for native localStorage consent changes. A current rejection or consent-storage removal stops collection, removes this controller's pending commands and sets Google's measurement-specific disable flag without reloading. An optional, same-origin `BroadcastChannel` carries only a strictly validated versioned withdrawal message and timestamp, allowing notification even if the sending tab cannot write storage. Receiving tabs attempt to persist rejection independently; they do not broadcast it again. Acceptance messages never start tracking or bypass the normal matching-record and verified-storage process. Stale, future-dated, malformed and unsupported channel messages are ignored. Once withdrawn, a document stays disabled for its lifetime, including after a later explicit acceptance saved for a future visit.

An already-sent request cannot be recalled. Removing a script element does not necessarily unload already-executed third-party code; the disable flag and pending-command cancellation stop further application-managed collection. Browser delivery is asynchronous: suspended tabs may receive notification only when resumed. If both storage notifications and BroadcastChannel are unavailable or blocked, immediate cross-tab notification cannot be guaranteed. If every storage mechanism refuses writes, no durable withdrawal marker can be guaranteed after storage later recovers; tracking remains off in notified documents and restoration fails closed while storage is unavailable. Before activation, test withdrawal across two real browser tabs, including a suspended tab, storage failures and reloads. GA4 remains disabled until the separate policy, account-settings and activation approvals are complete.
