# Golden Munnar Palace implementation review

Prepared against `6b782b0141f3f70f42ab08583cdc3f1e9009d5d8` (the inspected default branch and main HEAD).
Prepared for the authorized GitHub rollout. Production deployment status is reported
from GitHub checks; no direct remote D1, DNS or Cloudflare dashboard operation is used.

## Scope and model

Existing Hono, D1, session authentication, layout/CSS, properties, rooms and R2 media
are reused. No public redesign, new Customer Login, LeadVyne integration or online
booking/payment has been implemented. Changes to rate access are scoped to
`catalogue_only` properties; existing unrelated roles and properties retain their
behaviour.

Migration `0008_property_catalogue.sql`:

- Makes `rooms.capacity`, `min_nights`, `extra_bed` and property `checkin_time`,
  `checkout_time`, `id_required`, `pet_friendly`, `family_friendly` nullable. The
  copy/drop/rename statements preserve every existing value and the original defaults
  for legacy records; explicit NULL is allowed for unknown catalogue details. No primary
  key or foreign-key table rebuild occurs.
- Adds property `catalogue_only`, `classification`, and room `rack_basis`.
- Adds `catalogue_rate_periods` with independent nullable Staff and B2B values,
  date periods and per-tier basis. These do not enter legacy season/markup calculations.
- Adds `property_charges` with one shared price, optional separate child price,
  charging basis, CPAI label, dates, mandatory flag and arrangement locations.
- Adds scoped database triggers preventing catalogue rooms/properties from being
  used in quotes/bookings or storing internal rates in legacy room columns.

## Property data

The private source is `data/golden-munnar-palace.json`. It contains the client's
supplied property details, all four exact categories, units 68/17/10/3 (98 total),
Rack Rates 7000/11000/15000/19000 + GST, the exact supplied Staff/B2B periods,
16 public charges/arrangements and the exact cancellation policy.

`seed/golden-munnar-palace.sql` is generated by
`scripts/generate-golden-munnar.mjs`. It inserts only missing records by canonical
property slug, exact room name, room/date period and charge key. Repeating it
preserves existing edits and photo records. A same-name/slug conflict with another
record aborts for review. It does not run the demo seed or automatic rate importer.
The resulting property is marked live **only in the target database where this import
is explicitly executed**. It has been executed against local D1 only.

The legacy `base_rate` adapter equals the supplied Rack Rate, never a marked-up
selling price. `rooms.staff_rate` and `net_rate` remain NULL; confidential catalogue
periods are stored separately so legacy exports cannot accidentally read them.
There is no undated Staff/B2B fallback. April and June–September are separate periods;
May Staff Rates remain NULL. Dates outside supplied periods return NULL.

Because the GitHub repository is public, the actual client rate source and generated
SQL are gitignored and must be delivered privately, never committed or placed under
`public/`. Public CI uses `test/fixtures/catalogue.synthetic.json`, explicitly marked
with synthetic internal rates. Local tests select the private source when available
and validate the real supplied import. Synthetic fixtures cannot generate an import
file through the generator's normal output mode.

## Access and rendering

`src/lib/property-catalogue.ts` selects public room/rack data explicitly. Public
requests do not query internal periods. Manager/Sales select Staff columns only;
Admin alone selects B2B columns. Existing `view_net_rates` overrides cannot widen
this policy. Accounts receives no Staff or B2B data through this catalogue model.

The public property page, room share page and price endpoint always use the public
projection, including when the caller happens to be logged in as Admin. The staff
catalogue editor uses the authenticated server-side role; internal responses are
private/no-store. Non-admin attempts to submit B2B fields are rejected. Updates are
scoped to the property and room/period/photo IDs, and audit records contain no prices.
Shared knowledge-base documents use the public projection and omit unknown policy
assertions.

Public pricing is Rack only, plus the supplied public charges. All roles see identical
additional/add-on/festive charges. No markup, tier conversion, supplement fallback,
occupancy calculation or generated GST total is applied. Diwali and Christmas
supplements remain per room/night. The mandatory 24 Dec and 31 Dec adult/child
charges remain separate records, not part of the Rack Rate.

Staff can manage supplied property/room details, inventory, Rack/Staff prices,
shared charges, and approved photo uploads/mapping/deletion. Admin can additionally
manage B2B prices. Legacy import/edit/duplicate paths are blocked for catalogue
records; quote/booking price loading refuses them. Existing staff Rooms & photos
and Admin Properties paths lead to the catalogue editor. The legacy quote finder
links to catalogue information instead of offering Add to quotation for this property.

coordinates, beds, sizes and times remain NULL. The Duplex only has its supplied
4-Pax capacity. Classification stays exactly “5-Star facility hotel”, not a certified
star-category claim. Staff tax/meal basis and unsupplied charging units for some
extras/arrangements remain NULL; their prices and supplied wording are displayed
without invented units. These do not block information-only catalogue use.

Approved images are still pending. No property image URL, placeholder or stock
image is inserted. After approved application, open Staff → Rooms & photos →
Golden Munnar Palace (or Admin → Properties → the property) and use Property and
room photos. The existing `storeMedia` function uploads to the existing R2 `MEDIA`
binding using `properties/{propertyId}/{category}/{uuid}.{extension}` and stores the
association in `property_photos`.

Choose facade/common/pool/view/restaurant/activities/other for property images.
Choose room plus the exact Executive, Suite, Honeymoon Suite or Duplex category
for room images. Room selections are validated against this property's room IDs.
Use captions and the mapping form to correct associations. Supported image types
are JPEG/PNG/WebP, up to 15 MB per image and 20 files per request.
Recommended local source names are `golden-munnar-palace-exterior-01.jpg`,
`golden-munnar-palace-pool-01.jpg`, and corresponding `executive`, `suite`,
`honeymoon-suite`, `duplex` numbered filenames. R2 keys are generated by uploads;
source filenames are not assumed to be URLs.

## Applying to D1 after explicit approval

No following remote command has been executed.

1. Review the code diff and the private source/generated SQL. Confirm the existing
   account and D1 binding, pending migrations and a recoverable database snapshot.
   Check for an existing property by both name and slug; resolve any collision first.
2. Apply the reviewed migration to the approved existing D1. Do not use setup scripts
   or create another database. The migration preserves the behaviour of the old Worker
   while the new property is not yet inserted.
3. Deploy the separately approved application version before inserting the property,
   so its catalogue guards and role-filtered routes are already active.
4. Transfer the real source/SQL privately and execute only the targeted import against
   that approved D1. Never execute the synthetic fixture or full demo seed.
5. Verify the property/room/period/charge counts and private/public access with actual
   Admin, Manager and Sales accounts, then attach the approved images.

Once the correct existing binding has been confirmed, the commands are:

```sh
node scripts/generate-golden-munnar.mjs
npx wrangler d1 migrations apply gosanchari --remote -c wrangler.toml
# Approved application deployment occurs before the next command.
npx wrangler d1 execute gosanchari --remote -c wrangler.toml --file=seed/golden-munnar-palace.sql
```

The generator has no database connection and cannot deploy. It only generates SQL.
The remote application procedure remains subject to explicit approval.
